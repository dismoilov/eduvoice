# Архитектура

Документ объясняет, как устроен мост, какие решения приняты и почему. Код и этот текст
согласованы: у каждого модуля есть docstring с тем же объяснением на английском.

## 1. Из чего состоит система

| Слой | Что делает | Где |
|---|---|---|
| Телефония | принимает звонок, ведёт запись, держит очередь операторов | Asterisk 20.4 / FreePBX 16, `asterisk/extensions_custom.conf` |
| Мост | слушает звук, ведёт диалог, решает, что делать со звонком | `eduvoice/`, сервис `eduvoice-bridge` |
| Речь и модель | распознавание, синтез, языковая модель | VoiceLab.uz (`eduvoice/voicelab.py`) или заглушки |
| Содержимое | служебные фразы; ответы по регламентам — в базе, редактируются в CRM | `content/prompts.yaml`, таблица `knowledge` |
| Данные | звонки, реплики, граждане, обращения, база знаний, журнал действий | SQLite `/opt/eduvoice/data/eduvoice.db` (`store/`) |
| CRM | рабочее место call-центра | `crm/`, сервис `eduvoice-crm`, порт 9095 |

Мост и Asterisk живут на одной машине и общаются только через `127.0.0.1`: наружу не
открыт ни один порт моста.

## 2. Два канала между Asterisk и мостом

AudioSocket — очень простой протокол: один байт типа, два байта длины, дальше данные.

```
0x01  UUID звонка (16 байт) — приходит первым
0x10  звук, 20 мс. Тестовый канал Local/ — PCM s16le 8 кГц (320 байт);
      настоящий телефон — G.711 (160 байт), мост раскодирует сам
0x00  завершение
```

Через него идёт **только звук**. Ни номера звонящего, ни DTMF, ни переменных канала в
нём нет — поэтому всё остальное ходит по HTTP через функцию `CURL()` диалплана:

```
POST /calls/{uuid}/start   caller=998901234567   → «ok»      (до начала разговора)
GET  /calls/{uuid}/next                          → operator | hangup   (после)
GET  /calls/{uuid}/summary                       → JSON звонка
GET  /health                                     → состояние сервиса
```

Ключевая деталь безопасности: на запрос о неизвестном звонке API отвечает `operator`.
Даже если мост потерял состояние, звонящий попадёт к человеку, а не в тишину.

## 3. Жизнь одного звонка

```
Asterisk                     eduvoice/session.py                     провайдеры
   │
   ├─ UUID ────────────────► _begin: регистрация звонка
   │                          открыть распознавание ──────────────► stt.open()
   │                          прогреть синтез      ──────────────► tts.warm_up()
   │ ◄──── приветствие ────── греет из кэша (0 мс синтеза)
   │
   ├─ звук 20 мс ──────────► listening: webrtcvad ищет границы фразы
   │       …                  700 мс тишины = конец фразы
   │                         ┌──────────────────────────────────┐
   │                         │ thinking (в отдельной задаче)    │
   │                         │  8→16 кГц, распознать ───────────┼──► stt.transcribe()
   │ ◄──── «минуту…» ─────── │  если >1.2 с — фраза-заполнитель │
   │                         │  решение: ключевые слова / модель┼──► model.complete_json()
   │                         └──────────────────────────────────┘
   │ ◄──── ответ ──────────── speaking: синтез 24→8 кГц потоком ─► tts.stream()
   │ ──── человек заговорил ► barge-in: замолчать, слушать
   │
   │ ◄──── прощание ──────── closing: записать решение, 0x00
   ├─ GET /next → hangup|operator
```

Пока идёт распознавание и синтез, цикл чтения кадров не блокируется ни на миллисекунду:
всё медленное вынесено в задачи. Иначе перебивание приходило бы с опозданием, и человек
говорил бы в бота, который его не слышит.

## 4. Почему так, а не иначе

**AudioSocket, а не ARI/внешний медиасервер.** Нужен только звук в обе стороны; ARI
потребовал бы отдельный медиапоток и куда больше кода. AudioSocket встроен в Asterisk 20.

**`Dial(AudioSocket/...)`, а не приложение `AudioSocket()`.** Проверено на сервере: если
мост умирает посреди разговора, приложение `AudioSocket()` завершает звонок с ошибкой и
человек слышит гудки. `Dial(...,,g)` возвращает управление диалплану, и звонок уходит на
оператора. Проверка воспроизводится: остановить `eduvoice-bridge` во время звонка.

**Свой детектор границ фразы.** У VoiceLab нет промежуточных результатов распознавания,
поэтому момент «человек договорил» определяет мост: `webrtcvad` с гистерезисом (одиночный
шумный кадр не начинает и не заканчивает фразу) плюс 300 мс «предзаписи», чтобы не
срезать первый слог. `webrtcvad` — единственный VAD, который ставится на сервер
(Sangoma Linux 7, glibc 2.17); Silero/onnxruntime там не собираются.

**Кэш служебных фраз.** Приветствие, «минуту», прощание синтезируются один раз при старте
и хранятся как готовый PCM 8 кГц. Самая дешёвая экономия задержки: приветствие начинается
мгновенно.

**Ровная подача звука.** Asterisk играет то, что получает, в темпе получения. Поэтому
`AudioOut` отдаёт ровно один кадр в 20 мс; быстрее — человек услышит «кашу», медленнее —
паузы. Очередь можно мгновенно сбросить — так работает перебивание.

**Один поток ресемплинга на фразу.** Синтез приходит кусками; если пересчитывать каждый
кусок отдельно, на стыках возникают щелчки. `StreamResampler` держит состояние фильтра
между кусками (проверено тестом: результат совпадает с пересчётом целого буфера).

**Заглушки провайдеров.** Весь диалог, телефония и отказоустойчивость отлаживались на
заглушках, до того как появился ключ VoiceLab; на них же гоняются все тесты — ни ключа,
ни сети они не требуют. Переключение — одна переменная `EDUVOICE_PROVIDER`.

**HTTP-сервер без зависимостей.** Три ручки на голом asyncio: на сервере с glibc 2.17
новые колёса часто не ставятся, а тащить веб-фреймворк ради трёх строк ответа незачем.

## 5. Модель решает, но не распоряжается

Модель возвращает только JSON вида
`{"intent": "faq|answer|operator|repeat|goodbye|unclear|out_of_scope", "faq_id": …, "answer": …}`.
Что произойдёт со звонком, решает код (`eduvoice/brain.py`):

- `faq` с несуществующим `faq_id` → переспросить, **не** озвучивать выдумку;
- `answer` с пустым текстом → переспросить;
- незнакомый intent → переспросить;
- два непонятых вопроса подряд → оператор;
- больше 8 реплик → оператор;
- ошибка или таймаут модели → оператор.

То есть модель физически не может «придумать» норму закона и не может сама положить
трубку. Ответы по регламентам берутся из базы знаний CRM — там у каждого указан документ
и пункт (задача №3 перечня); `content/faq.yaml` остаётся резервом на случай недоступной
базы и первичной установки.

Отдельно: очевидные вопросы (по ключевым словам) отвечаются вообще без модели — это
экономит около секунды и делает самый частый сценарий самым быстрым.

## 6. Бюджет задержки

| Этап | На заглушках | Замерено с VoiceLab |
|---|---|---|
| Конец фразы → отправка в распознавание | 700 мс (настраивается) | 700 мс |
| Распознавание | 300 мс | 0.9–1.6 с |
| Решение (ключевые слова) | 0 мс | 0 мс |
| Решение (модель) | 400 мс | 0.8–1.5 с (две генерации разом на аккаунт) |
| Первый звук ответа (фраза из кэша) | 0 мс | 0 мс |
| Первый звук ответа (синтез) | 200 мс | 0 мс: все постоянные фразы синтезированы заранее |

Измерено на живых звонках 18.09 с настоящей узбекской речью: вопрос про стипендию —
863 мс до решения, академический отпуск — 1102 мс, просьба оператора — 1646 мс.
Каждый звонок пишет эти числа в `logs/YYYYMMDD.jsonl`, поэтому цифры в презентации —
не оценка, а замер.

## 6b. Сколько звонков система держит одновременно

Измерено настоящими сессиями по настоящему TCP: замерялись промежутки между кадрами по
20 мс, то есть ровно то, что слышит человек в трубке.

| Одновременных звонков | Медианный промежуток | Кадров с опозданием >40 мс |
|---|---|---|
| 20 | 20,0 мс | 0,0% |
| 60 | 20,0 мс | 0,0% |
| 120 | 20,0 мс | 0,0% |
| 150 | 20,0 мс | 0,8% |

Собственный механизм моста не является узким местом. **Настоящий потолок — аккаунт
VoiceLab: восемь одновременных вопросов, требующих языковой модели.** Девятый ждёт пять
секунд и переводится на оператора — поведение верное (человек не остаётся в тишине), но
это именно обрыв, и он назван здесь, чтобы не быть неожиданностью.

Важная деталь: вопросы, на которые отвечает быстрый путь по ключевым словам, модель не
трогают вовсе. На шести опубликованных темах это большинство звонков, поэтому потолок
достигается только потоком нестандартных вопросов.

Что сделать для промышленной эксплуатации: увеличить лимит аккаунта, а ожидание в очереди
к модели считать отдельно от таймаута самого запроса — сейчас они делят один бюджет в
пять секунд, поэтому исчерпание лимита выглядит как перевод на оператора, а не как
короткое ожидание.

## 6a. Как связаны помощник и CRM

```
   мост (eduvoice-bridge)                 CRM (eduvoice-crm)
        │  пишет звонок, реплики,              │  читает звонки и расшифровки
        │  привязку к гражданину               │  ведёт обращения и граждан
        ▼                                      ▼
   ┌──────────────────── SQLite (WAL) ────────────────────┐
   │  calls · turns · contacts · tickets · knowledge · audit │
   └──────────────────────────────────────────────────────┘
        ▲                                      │
        │  читает ТОЛЬКО опубликованные        │  супервайзер правит и публикует
        └──────── ответы (раз в 10 с) ─────────┘
```

Два процесса намеренно разделены: перезапуск CRM не может уронить разговор, а падение
CRM не мешает помощнику отвечать. Общего у них ровно одно — файл базы.

## 7. Что где лежит в коде

| Файл | Ответственность | Ключевое место |
|---|---|---|
| `main.py` | запуск, выбор провайдеров, прогрев фраз | `make_call_handler` — упавший звонок не роняет сервис |
| `session.py` | конечный автомат звонка | `_finish` — решение записывается до всего, что может упасть |
| `audiosocket.py` | протокол и ровная подача звука | `AudioOut._run` — кадр в 20 мс, `clear()` для перебивания |
| `vad.py` | границы фразы, перебивание | `SpeechDetector.push`, `seed` (не терять начало перебитой фразы) |
| `audio.py` | PCM-арифметика | `StreamResampler`, `FrameSplitter` (ни один байт не теряется) |
| `brain.py` | решения | `_from_intent` — правила поверх модели |
| `control_api.py` | HTTP для диалплана | неизвестный звонок → `operator` |
| `registry.py` | состояние звонков | `DEFAULT_NEXT = "operator"`, активный звонок не вытесняется |
| `prompts.py` | фразы и их кэш | атомарная запись, блокировка на фразу |
| `calllog.py` | журнал звонков | никогда не бросает исключение |
| `store/db.py` | схема и миграции | WAL, `busy_timeout`, версия схемы в `user_version` |
| `store/write.py` | запись звонка в базу | ошибка базы не ломает звонок |
| `store/knowledge.py` | опубликованные ответы для помощника | кэш на 10 секунд, черновики не видны |
| `crm/repo.py` | все запросы CRM | одно место, где видно, что система делает с данными |

## 8. Граница между мостом и поставщиком речи

`eduvoice/interfaces.py` — единственный контракт. Мост ожидает три объекта:

```python
SpeechToText : open(language) / transcribe(pcm16k) -> Transcript / close()
TextToSpeech : warm_up(language) / stream(text, language) -> AsyncIterator[bytes] / close()
ChatModel    : complete_json(messages, timeout_s) -> dict
```

Частоты дискретизации зафиксированы (8 кГц телефония, 16 кГц распознавание, 24 кГц
синтез); пересчёт делает мост, провайдеры его не касаются. Любая ошибка провайдера должна
приходить как `SttError` / `TtsError` / `LlmError` — мост трактует их как «провайдер
недоступен» и переводит звонок на человека, а не падает. Проверено 18.09: при отрезанном
доступе к VoiceLab звонящий услышал узбекскую фразу о неполадке (она в кэше на диске) и
через 19 секунд говорил с оператором.
