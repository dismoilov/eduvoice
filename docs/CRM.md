# EduVoice CRM — рабочее место call-центра

CRM — это вторая половина системы. Первая (голосовой помощник) разговаривает с людьми,
вторая даёт сотрудникам министерства работать с тем, что помощник не закрыл сам, и
управлять тем, **что** он отвечает.

```
http://10.103.10.86:9095
```

| Роль | Логин | Что может |
|---|---|---|
| Администратор | `admin` | всё + сотрудники, роли, журнал действий |
| Супервайзер | `nazorat` | все звонки и обращения, аналитика, публикация базы знаний |
| Оператор | `operator` | свои обращения, звонки, карточки граждан |

Пароли — в `/root/eduvoice-credentials.txt` на сервере. Интерфейс двуязычный
(Oʻzbekcha / Русский) и с двумя темами, переключатели в шапке.

---

## 1. Главное: база знаний управляет ответами помощника

Супервайзер открывает **Базу знаний**, правит текст ответа, нажимает «Опубликовать» —
и **следующий звонящий слышит новую формулировку**. Ни перезапуска, ни программиста,
ни выкладки.

Проверено на живом сервере 18.09.2026:

```
14:37  звонок А → бот: «Stipendiya har oyning oʻninchi sanasida…»
14:38  правка ответа в CRM (мост не перезапускался, работает с 14:36:37)
14:38  звонок Б → бот: «Stipendiya har oyning yigirmanchi sanasida…»
```

Как это устроено: мост читает из базы только записи со статусом «опубликован», не чаще
раза в десять секунд и только если они менялись. Черновик не попадает к гражданину
никогда. Каждое сохранение создаёт новую версию, прежняя остаётся в истории — ответы
цитируют нормативные документы, поэтому «кто и когда это изменил» должно быть
восстановимо.

## 2. Экраны

**Рабочий стол.** Звонки за сегодня, вопросы, доля решённых без оператора, средний ответ,
открытые и просроченные обращения. Рядом — состояние голосового помощника (жив ли мост,
сколько звонков на линии) и список звонков, по которым обращение ещё не завели.

**Звонки.** Список с фильтрами и поиском **по тексту разговора** (полнотекстовый индекс
SQLite FTS5). В карточке: запись с плеером, пронумерованные метки вопросов, расшифровка
«вопрос → ответ помощника», источник ответа, задержки по этапам и кнопка «создать
обращение из звонка» — она же связывает обращение с гражданином.

**Обращения.** Очередь с фильтрами (статус, ответственный, просроченные, мои). В карточке —
смена статуса, назначение, приоритет, решение, комментарии. Всё в одной ленте: кто
поменял статус, кто назначил, кто что написал.

**Граждане.** Карточка заводится автоматически при первом звонке с номера. Внутри —
все звонки и обращения этого человека, заметки, категория (абитуриент, студент, родитель),
вуз. Оттуда же — кнопка **«Позвонить»**: Asterisk сначала звонит оператору на внутренний
номер, потом соединяет с гражданином.

**Аналитика.** Объём по дням и часам, распределение итогов, скорость ответа (среднее,
медиана, p90), частые темы и вопросы, нагрузка операторов, выгрузка CSV для отчёта.

**Администрирование.** Сотрудники, роли, внутренние номера, смена пароля и журнал
действий: кто вошёл, кто создал обращение, кто опубликовал ответ.

## 3. Как это сделано

| Решение | Почему так |
|---|---|
| **SQLite** `/opt/eduvoice/data/eduvoice.db` | одна машина, десятки звонков в минуту, ноль администрирования; режим WAL позволяет мосту и CRM писать одновременно |
| **FastAPI + Jinja2**, страницы рендерит сервер | десятки форм и таблиц; никакой сборки и npm — страница открывается на машине без интернета |
| **Отдельный сервис** `eduvoice-crm` на порту 9095 | перезапуск CRM не трогает звонки; откат — просто остановить сервис |
| **Пароли `hashlib.scrypt`, сессии на `hmac`** | обе функции в стандартной библиотеке, лишних зависимостей нет |
| **Мост пишет звонок в базу и в JSON-журнал** | двойная запись дешёвая и спасает, если база занята |
| **Полнотекстовый поиск FTS5** | найти «stipendiya» среди тысяч расшифровок — один запрос |
| **Click-to-call через ARI** | у Asterisk уже есть REST-интерфейс и наш пользователь |

Схема данных: `users`, `contacts`, `calls`, `turns`, `tickets`, `ticket_events`,
`knowledge`, `knowledge_versions`, `callbacks`, `audit`, `settings`. Миграции versioned
через `PRAGMA user_version` — повторный запуск ничего не ломает.

## 4. Безопасность и персональные данные

- вход по логину и паролю, пароли — scrypt со случайной солью;
- три роли: оператор не видит администрирования и аналитики, супервайзер — не видит
  администрирования (проверено тестами);
- каждая форма несёт токен, привязанный к сессии (защита от подделки запросов);
- перебор пароля тормозится: пять неудач — минута ожидания для этого логина;
- журнал действий: входы, неудачные входы, создание и изменение обращений, публикация
  ответов, звонки из CRM;
- имя записи проверяется дважды, выйти за каталог записей невозможно (тесты на
  `../../etc/passwd`);
- сервис работает не от `root`, с `NoNewPrivileges`, `ProtectSystem`, `ProtectHome`.

Чего сознательно нет на хакатоне: HTTPS (доступ по локальной сети), срока хранения
записей, двухфакторной аутентификации.

## 4a. Скорость

Замерено на 20 000 звонков, 40 000 реплик и 3 000 обращений — больше, чем call-центр
министерства получает за месяц:

| Страница | Время |
|---|---|
| Рабочий стол | 17 мс |
| Список звонков (и с фильтрами) | 6–10 мс |
| Граждане, обращения, база знаний | 3–11 мс |
| Аналитика за 30 дней | 170 мс |
| Фоновое обновление рабочего стола | 8 мс |

На сервере с реальными данными — 3–8 мс на страницу. Что для этого сделано: агрегаты
считаются в базе, а не в Python; добавлены индексы под фактические запросы; списки
постраничные; ответы сжимаются; проверка «жив ли голосовой помощник» кэшируется на
5 секунд, чтобы упавший мост не замедлял страницу. Подробности и история правок —
[AUDIT.md](AUDIT.md).

## 5. Эксплуатация

```bash
make deploy          # выкатить мост и CRM, перезапустить оба
make crm-logs        # живой лог CRM
make crm-restart
make backup          # согласованная копия базы на сервере
make sql Q="select count(*) from tickets"   # заглянуть в базу (системный sqlite3 её не читает, см. OPERATIONS.md)
make crm-user USER_LOGIN=olim USER_NAME="Olim" USER_ROLE=operator USER_PASSWORD=... USER_EXT=101
```

Первичное наполнение (делается один раз):

```bash
uv run python -m crm.cli user admin "Administrator" admin --password '…'
uv run python -m crm.cli import-history logs/           # перенос старых звонков
uv run python -m crm.cli import-knowledge content/faq.yaml --publish
```

Настройки — в `.env` на сервере: `CRM_HOST`, `CRM_PORT`, `CRM_SLA_HOURS`, `EDUVOICE_DB`,
`RECORDINGS_DIR`, `ARI_USER`, `ARI_PASSWORD`.

## 6. Проверка за пять минут

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://10.103.10.86:9095/calls        # 303 — без входа никак
# вход теперь требует токен формы — так же, как из браузера
CSRF=$(curl -s -c jar http://10.103.10.86:9095/login | grep -oE 'name="csrf" value="[^"]+"' \
       | head -1 | sed 's/.*value="//; s/"//')
curl -s -b jar -c jar -o /dev/null --data-urlencode "login=nazorat" \
     --data-urlencode "password=ПАРОЛЬ" --data-urlencode "csrf=$CSRF" \
     http://10.103.10.86:9095/login
curl -s -b jar http://10.103.10.86:9095/calls | grep -c 99890                  # звонки видны
curl -s -b jar -r 100-199 -D - -o /dev/null \
     http://10.103.10.86:9095/media/recordings/<uuid> | head -2                # 206 — перемотка
```

В браузере: войти супервайзером → **Звонки** → открыть звонок → нажать метку «▶ 0:12»
(запись перематывается на вопрос) → «Создать обращение из звонка» → в **Обращениях**
сменить статус и написать комментарий → в **Базе знаний** изменить ответ и опубликовать →
позвонить ещё раз и услышать новую формулировку.
